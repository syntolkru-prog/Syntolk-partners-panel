# Полный локальный тест партнёрской программы Syntolk

Проверено 7 октября 2026 года. Это тест настоящего локального приложения и базы данных, но без движения настоящих денег. CloudPayments и почтовый провайдер для него не нужны.

## Что уже проверено и исправлено

На отдельном партнёре выполнены регистрация через браузер, вход ключом, выдача программы, создание ссылки, настоящий переход, привязка клиента, регистрация клиента, первая и повторная оплаты, защита от дублирования оплаты, полный возврат, одобрение комиссии, расчёт выплаты, подтверждение, просмотр выплаты партнёром, защита от двойного подтверждения, отмена дополнительной заявки и проверка прав доступа.

Исправления: расчёт выбранного партнёра не захватывает остальных; ожидающая выплата больше не считается выплаченной; появилась отмена незавершённой заявки; после изменения начислений нельзя подтвердить устаревшую сумму; регистрации показываются отдельно от всех событий. Локальный портал передаёт `/r/...` счётчику переходов и выдаёт полный адрес ссылки. Исправлена ошибка переводчика интерфейса при появлении текстовых узлов.

Отчёт по последовательным локальным шагам: `.local-demo/results.json`. Ключ тестового партнёра и параметры текущего прогона: `.local-demo/state.json`. Папка исключена из Git. Помощник: `apps/api/scripts/local-demo.mts`, запуск `pnpm local:demo <команда>`.

## 1. Требования и запуск

Рабочая папка: `C:\Users\fxcom\Documents\Codex\Syntolk-partners-panel`.

Нужны установленный Node.js (для помощника с `loadEnvFile` — Node 22.15+ или 24+), менеджер pnpm, работающий Docker Desktop, зависимости проекта и существующий `.env`. Они уже используются работающей локальной версией. Новые платёжные ключи не нужны.

Адреса:

| Компонент | Адрес |
| --- | --- |
| Администратор | http://localhost:5673/login |
| Партнёр в отдельном локальном сеансе | http://127.0.0.1:5673/login |
| Регистрация партнёра | http://localhost:5673/join |
| API | http://127.0.0.1:4601 |
| Счётчик переходов напрямую | http://localhost:4701 |

Если сайт уже открыт и работает, повторно запускать службы не нужно. После перезагрузки компьютера:

```powershell
Set-Location 'C:\Users\fxcom\Documents\Codex\Syntolk-partners-panel'
docker compose up -d postgres
```

Затем в трёх отдельных окнах PowerShell, в той же папке:

```powershell
pnpm dev:api
```

```powershell
pnpm dev:router
```

```powershell
pnpm --filter @openpartner/portal dev --host 0.0.0.0
```

Окна с этими процессами оставьте работающими. `Ctrl+C` останавливает соответствующий процесс. Не запускайте вторую копию на занятом порту. Не запускайте мастер `/install` повторно на настроенной базе. Не используйте `docker compose down -v`: это удаляет данные PostgreSQL.

Установка зависимостей (`pnpm install`), сборка общего пакета (`pnpm --filter @openpartner/db build`) и `pnpm migrate` нужны при новом развёртывании/изменении схемы, а не перед каждым тестом. Для текущего сценария схема уже подготовлена.

## 2. Разделить роли

Администратор работает через `localhost:5673`, партнёр — через `127.0.0.1:5673`. Это одно приложение, но разные браузерные хранилища авторизации. Альтернатива — два разных браузера/профиля или приватное окно. Две обычные вкладки одного адреса не дают двух независимых аккаунтов.

На странице входа нажмите «Ключ администратора / партнёра», вставьте соответствующий ключ и войдите. Ключ действует до отзыва, а не 15 минут, как почтовая ссылка. Для существующего администратора используйте ранее выданный ключ. Тестовый партнёр получает отдельный ключ на шаге 4.

Сейчас почтовый транспорт — `none`: сообщение «Проверьте почту» не означает, что письмо реально отправлено. Приглашения и одноразовые ссылки выводятся в консоль API, а при запуске с журналированием — в `work/api-dev.log`. Для локального теста удобнее постоянный ключ; подключать SMTP не требуется.

## 3. Подготовить новый чистый прогон

В четвёртом окне PowerShell, в папке проекта:

```powershell
pnpm local:demo prepare
```

Команда создаёт новую отдельную программу с 20% за каждую оплату `invoice_paid`, регулярными начислениями, удержанием 0 дней, моделью `last_click`, окном атрибуции 60 дней и адресом перехода `http://localhost:5673/login`.

Запишите из результата `name`, `email`, `linkKey`, `userId` и `programId`. Это параметры именно вашего нового теста. Они также сохраняются в `.local-demo/state.json`. Старые партнёры и результаты не удаляются; состояние предыдущего прогона архивируется в той же локальной папке.

Для быстрого теста минимальная сумма выплаты должна быть 0 либо меньше ожидаемой комиссии. В текущей рабочей настройке порог — 0. Если измените порог, результат расчёта может сообщить «ниже порога» — это нормальная проверка правила, а не поломка.

## 4. Создать партнёра

### Через реальную публичную форму

1. Откройте `http://localhost:5673/join`.
2. Введите имя и email из `prepare`.
3. Заполните обязательные поля и подтвердите условия.
4. Отправьте форму.
5. В админке откройте «Партнёры» (`/admin/partners`), обновите страницу и найдите запись по email.

Сейчас включено автоматическое одобрение. Если позже включите ручную проверку, сначала одобрите заявку. Новый зарегистрированный партнёр не получает все программы автоматически: нужно выдать доступ к нужной программе.

Создайте ключ и выдайте подготовленную программу:

```powershell
pnpm local:demo access
pnpm local:demo grant
```

Первая команда выдаёт ключ именно партнёру с email текущего прогона. Вторая назначает только программу этого прогона. Войдите этим ключом через `http://127.0.0.1:5673/login`.

### Самостоятельно администратором

В админке есть «Партнёры» → «Пригласить партнёра». Укажите имя, email, телефон при необходимости и выбранные программы. Эта кнопка создаёт приглашение; для стандартной активации нужна одноразовая ссылка из локальной консоли API, так как настоящая почта не подключена.

Если хотите создать тестового активного партнёра без письма, вместо публичной регистрации после `prepare` выполните:

```powershell
pnpm local:demo create
pnpm local:demo access
```

`create` создаёт активного партнёра и сразу выдаёт тестовую программу. Не выполняйте `create` после уже сделанной регистрации того же email: получится конфликт дубликата.

Для любого уже созданного партнёра ключ можно выдать командой `pnpm local:demo access 'его-email'`, но это меняет выбранного партнёра помощника. Не подменяйте партнёра посреди фиксированного тестового сценария.

## 5. Создать настоящую учитываемую ссылку

В кабинете партнёра:

1. «Ссылки» → «Новая ссылка».
2. Выберите программу «Локальная проверка 20% ...» вашего прогона.
3. «Название ссылки»: например, «Проверка YouTube».
4. «Канал»: `youtube`.
5. «Ключ ссылки»: точный `linkKey` из `prepare`, без `/r/` и без домена.
6. «Создать ссылку».

Не вводите полный URL в поле ключа. Используйте уникальный ключ латиницей/цифрами, например `local_...-youtube`. Для повторного теста не используйте ключ уже существующей ссылки.

В таблице появится полный адрес, например `http://127.0.0.1:5673/r/local_...-youtube`. Его можно открыть как обычную ссылку или скопировать кнопкой рядом. Если браузер запрещает буфер обмена, скопируйте адрес самой ссылки через контекстное меню.

Администратор создаёт ссылку так же: «Партнёры» → строка партнёра → «Ссылки». Общий раздел `/links` у администратора сначала показывает выбор партнёра — это не кабинет конкретного партнёра.

```powershell
pnpm local:demo links
```

Команда проверяет, что создана именно ссылка текущего теста.

## 6. Сделать настоящий переход в браузере

1. Откройте полный адрес `/r/<linkKey>` в отдельной вкладке.
2. Должен произойти редирект на `http://localhost:5673/login?cref=...`.
3. Скопируйте значение `cref` из адресной строки — это ID конкретного клика.
4. В кабинете партнёра обновите «Главная»: «Переходы» должно стать 1.
5. Прокрутите до «Эффективность ссылок»: напротив этого ключа тоже будет 1 переход.
6. В админке откройте «Карточка» нужного партнёра: там также появится переход.

Можно использовать и прямой адрес счётчика `http://localhost:4701/r/<linkKey>`. Теперь оба локальных варианта считают переходы.

Повторное открытие реферального адреса — ещё один переход. Это число запросов, не уникальных людей. Обновление уже открытой конечной страницы `/login?cref=...` не обращается повторно к `/r/...`. Не делайте десятки быстрых кликов: проверка мошенничества может пометить такой трафик и не начислять комиссию.

## 7. Имитировать регистрацию привлечённого клиента

Регистрация партнёра через `/join` и регистрация клиента, которого он привёл, — разные операции.

Сейчас реальная регистрация на `syntolk.ru` не подключена к этой локальной базе. Поэтому в проверке выполняем две реальные операции API: связываем клик с ID тестового клиента и отправляем событие `signup`:

```powershell
pnpm local:demo register 'ЗНАЧЕНИЕ_cref_ИЗ_АДРЕСА'
```

Результат: 1 переход, 1 регистрация, 0 ₽ комиссии. Команда не создаёт аккаунт в рабочем Syntolk: она создаёт локальную привязку и регистрационное событие в партнёрской системе. Просто посетить `syntolk.ru` недостаточно, чтобы локально засчитать регистрацию.

В дальнейших оплатах используйте один и тот же `userId` из `prepare`. Для другого клиента нужен новый ID. Для проверки другой ссылки с другим клиентом также нужен новый ID — уже привязанный клиент сохраняет свою первоначальную привязку.

## 8. Имитировать оплату и начисление 20%

В админке откройте «Тестовые платежи» (`http://localhost:5673/admin/payment-simulator`): выберите тестового партнёра, его ссылку, введите `userId` текущего прогона и сумму в рублях. Кнопка — «Провести тестовый платёж».

При 1 000 ₽ комиссия должна быть 200 ₽, при дополнительной оплате 1 500 ₽ того же клиента — ещё 300 ₽. Обновите кабинет партнёра и раздел «Комиссии»: появятся начисления «ожидает подтверждения», число платящих клиентов останется 1.

Для строгой проверки с автоматической фиксацией результатов используйте команды **вместо соответствующих нажатий кнопки**, не вместе с ними:

```powershell
pnpm local:demo first
pnpm local:demo replay
pnpm local:demo repeat
```

Порядок важен:

| Шаг | Ожидаемый результат |
| --- | --- |
| `first`: оплата 1 000 ₽ | начислено 200 ₽ |
| `replay`: тот же ID платёжного события | по-прежнему 200 ₽, второй комиссии нет |
| `repeat`: новая оплата 1 500 ₽ | начислено всего 500 ₽ |

Дважды нажать кнопку интерфейса — это две разные тестовые оплаты, а не повторная доставка одной оплаты. Защиту от дубля проверяет `replay`, где ID события остаётся одинаковым.

Если оплатить нового, ещё не привязанного клиента через симулятор, он сам создаст технический клик. Поэтому для проверки именно браузерного клика сначала выполните шаги 6–7. Сам симулятор оплаты не создаёт событие регистрации.

## 9. Проверить возврат до выплаты

Для фиксированного сценария после `repeat`:

```powershell
pnpm local:demo refund
```

Команда возвращает вторую оплату 1 500 ₽, отменяет её комиссию 300 ₽, проверяет повторную доставку возврата. Должно остаться 200 ₽.

В интерфейсе доступна «Вернуть последний платёж»: она относится только к последней оплате, сделанной на этой открытой странице симулятора. После обновления страницы память о последнем платеже теряется. Командные оплаты помощника не являются «последним платежом» этой формы.

Показатель выручки сейчас отображает первоначальные оплаты **до вычета возвратов**, а не чистую выручку. Поэтому после оплаты 1 000 + 1 500 и возврата 1 500 выручка останется 2 500 ₽, но комиссия правильно станет 200 ₽. Не используйте показатель валовой выручки как банковский остаток.

## 10. Одобрить комиссию

Админка → «Очередь проверки» (`/admin/review`) → нужное начисление → «Подтвердить». Для подготовленной программы удержание 0 дней, поэтому ждать месяц не надо.

В фиксированном сценарии вместо нажатия можно выполнить:

```powershell
pnpm local:demo approve
```

Партнёр должен увидеть «Доступно к выплате 200 ₽», «Выплачено 0 ₽». При удержании 30 дней одобрение до истечения срока блокируется — это настройка программы, а не ограничение локального запуска.

## 11. Выплатить партнёру в режиме имитации

1. Админка → «Партнёры» → именно тестовый партнёр → «Выплаты».
2. Убедитесь, что в адресе есть `?partnerId=<ID_нужного_партнёра>`.
3. Нажмите «Рассчитать выплаты».
4. Появится заявка 200 ₽, метод «Вручную», статус «ожидает».
5. Обновите партнёрский кабинет: «Доступно 0 ₽», «Ожидает выплаты 200 ₽», «Выплачено 0 ₽».
6. У администратора нажмите «Подтвердить» в строке этой заявки.
7. Заявка станет «выплачено», появится дата завершения.
8. У партнёра обновите «Выплаты» и «Главная»: выплачено 200 ₽, ожидает 0 ₽.

Проверки фиксированного сценария:

```powershell
pnpm local:demo payout-check
pnpm local:demo pending-fixed
```

Эти две команды запускаются **между расчётом и подтверждением**. После подтверждения:

```powershell
pnpm local:demo confirmed
pnpm local:demo safe-replay
pnpm local:demo scope
```

`safe-replay` проверяет, что новый расчёт не выплачивает ту же комиссию повторно и повторное подтверждение отвергается. `scope` проверяет запрет партнёру запускать выплаты и читать историю другого партнёра (нужна хотя бы ещё одна запись партнёра).

На общем экране `/payouts` без `partnerId` расчёт относится ко всем доступным начислениям компании. Для изолированного теста обязательно открывайте выплаты конкретного партнёра.

«Подтвердить» — только запись в локальном учёте. Баланс карты, счёта или CloudPayments не меняется. Никакой настоящий банковский перевод эти действия не делают.

## 12. Отмена ожидающей заявки

Пока заявка «ожидает», администратор может нажать «Отменить заявку». Она остаётся в истории как отменённая, а невыплаченные комиссии снова доступны для расчёта. В базе для совместимости используется статус `failed` с причиной `manual_cancel`; интерфейс показывает «отменена».

Если после расчёта прошёл возврат и сумма начислений изменилась, приложение откажется подтверждать старую сумму. Отмените незавершённую заявку и выполните расчёт заново. Уже завершённую выплату таким способом отменить нельзя.

Дополнительный автоматический тест после `confirmed`:

```powershell
pnpm local:demo cancel-check
```

Он добавляет вспомогательную оплату 500 ₽ (комиссия 100 ₽), рассчитывает и отменяет её заявку, затем возвращает вспомогательную оплату. Первоначальные выплаченные 200 ₽ сохраняются. Это создаёт дополнительные записи, которые не следует путать с повторной выплатой.

## 13. Где смотреть и как продолжать

Партнёр: «Главная» → переходы, регистрации, платящие клиенты, доступный/ожидающий/выплаченный баланс; ниже «Эффективность ссылок». «Комиссии» → начисления; «Выплаты» → история заявок.

Администратор: «Партнёры» → «Карточка» → сводка и история; «Ссылки» → ссылки конкретного партнёра; «Очередь проверки» → одобрение; «Выплаты» → расчёт/подтверждение/отмена; «Тестовые платежи» → произвольные суммы.

Обновляйте страницы после действий в другом кабинете — это не потоковая синхронизация между браузерами.

```powershell
pnpm local:demo status
```

Показывает текущее состояние выбранного тестового партнёра без новых платежей. Для повторения чистого фиксированного сценария начните с нового `prepare` и нового партнёра, не с повторного `first` на уже завершённом сценарии.

## 14. Ограничения и следующий шаг к рабочему Syntolk

Для локального теста достаточно текущего приложения, PostgreSQL, двух сеансов и тестового помощника. Не нужны CloudPayments, SMTP, публичный домен или API реального Syntolk.

Но это ещё не доказательство готовности настоящих выплат. Для рабочего сервиса отдельно нужны:

- внешний HTTPS-адрес кабинета и маршрутизация `/r`;
- сохранение `cref` при заходе на Syntolk и отправка `identify` + `signup` при реальной регистрации;
- стабильный ID клиента в Syntolk и платёжных событиях;
- проверенные уведомления успешной оплаты/повторной оплаты/возврата из платёжной системы;
- согласованный и подключённый механизм настоящих выплат партнёрам, их реквизиты и подтверждение провайдера;
- рабочая почта либо другой штатный способ входа;
- полноценная сверка возвратов после уже состоявшейся выплаты, накопительных частичных возвратов и отрицательного остатка;
- резервное копирование, права доступа и настройки безопасности перед открытием наружу.

Последующие удержания после возврата уже выплаченной комиссии сейчас не следует считать готовым автоматическим взаимозачётом: отрицательная корректировка учитывается, но её взыскание из будущих выплат требует отдельной реализации и проверки. Аналогично валовая выручка не является отчётом о чистом денежном потоке.

Исходные проверки интеграции очищают тестовые таблицы. Их запускайте только в отдельной базе, никогда в рабочей `openpartner`. Для этого аудита создана база `syntolk_local_audit_20261007_test`; записи ваших существующих партнёров не очищались.
