## Подтверждённые ошибки

### C01. Одна заготовка превращается в два подготовленных материала — P1

**Воспроизведение:** загрузить одну заготовку без даты → отметить «Материал готов» → сохранить → прикрепить её к пустой задаче из плана.

До назначения API фактов возвращает `preparedMaterials: 1`. После назначения — `preparedMaterials: 2`, хотя календарь содержит один готовый материал с двумя перенесёнными файлами. После подготовки второго материала общий факт показывает 3 подготовленных вместо 2. В области одного сценария ошибка может быть незаметна, если исходная заготовка была без сценария; в области «Весь контент» она видна.

**Причина:** исходная заготовка архивируется с `assignedToMaterialId`, но сохраняет `preparedAt`. Выборка готовности читает обе записи без исключения замещённого источника.

**Код:** [calculator-current-values.ts](../../apps/api/src/calculator-current-values.ts), строка 26; [work-calendar.ts](../../apps/api/src/work-calendar.ts), строки 79–99.

**Исправление:** считать назначенный материал один раз; исключать замещённую исходную заготовку по связи назначения, сохраняя законную историю других архивных материалов. Отдельно сохранить первоначальную дату подготовки при переносе. Последний аспект установлен по коду: сейчас целевой `preparedAt` устанавливается заново; граница разных календарных дней отдельно не воспроизводилась.

**Доказательства:** [до назначения](../../outputs/calendar-flow-audit-ready.json), [после назначения](../../outputs/calendar-flow-audit-assigned.json).

### C02. Ручной материал на сегодня отсутствует на главной — P1

**Воспроизведение:** в календаре добавить материал, выбрать существующий сценарий, назначить сегодняшний день, сохранить. Открыть главную.

Календарь показывает «Ручной материал на сегодня» на 25 октября. Главная пишет «На сегодня задач нет» и предлагает ближайшую старую задачу на 30 октября. Совпадение сценария проверено. Публикация ручного материала также не добавляет его в блок дня.

**Причина:** главная запрашивает `/coach/me/calculator-plan` и строит рабочий день по `CoachTask`. Новый материал календаря существует в `PartnerMaterial`, но не представлен в этом наборе задач.

**Код:** [CoachDay.tsx](../../apps/portal/src/pages/coach/CoachDay.tsx), строки 29–43; создание самостоятельного материала — [materials-service.ts](../../apps/api/src/materials-service.ts), строка 47.

**Исправление:** согласовать источник задач главной с календарём, сохранив выбранные программу/сценарий и исключив дубли старых задач и материалов. Прогноз калькулятора от ручной задачи автоматически пересчитывать не нужно.

**Доказательство:** [главная без существующей ручной задачи](../../outputs/calendar-audit-home-missing-manual.png).

### C03. Возврат не восстанавливает вкладку, карточку и фильтры — P2

**Воспроизведены три случая:**

1. Из калькулятора открыть календарь → «Материалы» → Back. Возврат сразу в калькулятор, а не в «План».
2. Открыть материал → «Публикация» → «Результаты» → Back. Возвращается календарь без открытого материала и вкладки публикации.
3. Выбрать формат, статус и поиск «Ручной» → перейти в «Результаты» → Back. Поиск, формат и статус сброшены.

При Back между URL одного календаря также возможно расхождение адреса и открытого состояния: URL уже без `section=materials`, а библиотека/карточка ещё открыта.

**Причина:** часть состояния читается из URL только при первом монтировании, часть существует только в React state. Переключения раздела и периода используют `replace`, открытие карточки не записывает `materialId` в адрес.

**Код:** [CalendarWorkspace.tsx](../../apps/portal/src/pages/coach/CalendarWorkspace.tsx), строки 24–42, 70–79; локальная вкладка карточки — [CalendarMaterialDialogs.tsx](../../apps/portal/src/pages/coach/CalendarMaterialDialogs.tsx), строка 34.

**Исправление:** единообразно хранить навигационное состояние и восстанавливать его при Back/Forward; отдельно определить, какие действия создают запись истории. Ввод каждой буквы поиска не должен засорять историю.

### C04. Back теряет несохранённый текст без предупреждения — P1

**Воспроизведение:** открыть заготовку → изменить «Текст материала», убедиться в статусе «Есть изменения» → вернуться браузером до другой страницы → Forward/повторное открытие.

Тестовый текст `НЕСОХРАНЁННАЯ ПРОВЕРКА ВОЗВРАТА` исчез. После повторного открытия значение поля пустое. При смене URL внутри календаря карточка некоторое время сохранялась; потеря произошла при уходе с маршрута.

**Причина:** проверка `dirty` привязана к обработчику закрытия окна. Навигация браузера размонтирует компонент в обход этого обработчика.

**Код:** [CalendarMaterialDialogs.tsx](../../apps/portal/src/pages/coach/CalendarMaterialDialogs.tsx), строка 49; состояние окна — [CalendarWorkspace.tsx](../../apps/portal/src/pages/coach/CalendarWorkspace.tsx).

**Исправление:** защищать несохранённые изменения при уходе с маршрута и перезагрузке либо надёжно восстанавливать черновик. Обработку обычного JavaScript confirm в этом браузере не считаю полностью проверенной: инструмент управления столкнулся с ограничением при показе диалога. Факт потери при Back проверен отдельно без такого диалога.

### C05. Таблица регистраций теряет известную публикацию клиента — P2

В «Источниках трафика → Публикации и ссылки» правильно показаны два материала и их переходы. Переход по ручному материалу открывает «Результаты» с 2 переходами, 1 регистрацией, 700 ₽ оплат клиентов и 140 ₽ комиссии.

Но в «Последних регистрациях» и полном списке регистраций все четыре строки показывают «Источник не передан». У трёх регистраций связь с публикацией есть и подтверждена каноническим отчётом. Отсутствие HTTP Referer не означает отсутствие известной отслеживаемой публикации.

**Причина:** поле `source` таблицы строится только из `cl.referer`, не из `trackingSourceId` и метаданных материала/размещения. Такое ограничение особенно заметно при переходах из приложений и при прямом открытии ссылки.

**Код:** [partner-analytics.ts](../../apps/api/src/partner-analytics.ts), строки 497–501.

**Исправление:** отдавать таблице известные материал, размещение и основную ссылку; Referer оставить отдельным техническим источником либо запасным отображением. Не приписывать материал тем двум переходам, где его действительно нет.

### C06. Новая площадка размещения не попадает в поиск календаря — P2

**Воспроизведение:** материал с ВКонтакте → «Публикация» → «Добавить размещение» → «Дзен» → сохранить → в календаре поиск «Дзен».

Внутри карточки есть обе площадки, статус корректно становится «Частично опубликовано», но поиск возвращает 0 материалов. Текст карточки календаря по-прежнему перечисляет только ВКонтакте.

**Причина:** календарь берёт первоначальный `material.platforms`, а поиск проверяет только этот список. Добавленные фактические размещения участвуют в счётчике размещений, но не в отображаемых/поисковых площадках.

**Код:** [work-calendar.ts](../../apps/api/src/work-calendar.ts), строки 22–39; [work-calendar-model.ts](../../apps/portal/src/pages/coach/work-calendar-model.ts), строка 32; [CalendarWorkspace.tsx](../../apps/portal/src/pages/coach/CalendarWorkspace.tsx), строка 84.

**Исправление:** согласовать площадки календаря с первоначальным планом и текущими размещениями, без дублирования площадок и без потери повторных размещений.

### C07. После переноса задачи дата в автоматическом имени остаётся старой — P2

**Воспроизведение:** открыть `Пост · 30.10.2026 · №1` → изменить день на 25 октября, время на 18:45 → сохранить.

Материал переместился на 25 октября, время сохранилось, задача на главной появилась на сегодня. Но название осталось `Пост · 30.10.2026 · №1` — и в календаре, и на главной.

**Причина:** UI всегда отправляет `title` при сохранении. Backend трактует это как пользовательское имя и ставит `customTitle=true`; обновление даты в автозаголовке выполняется только при отсутствии `title` в запросе.

**Код:** [CalendarMaterialDialogs.tsx](../../apps/portal/src/pages/coach/CalendarMaterialDialogs.tsx), строка 47; [work-calendar.ts](../../apps/api/src/work-calendar.ts), строки 55–59.

**Исправление:** отличать фактическое переименование от отправки неизменённого заголовка. Пользовательские названия не переписывать.

### C08. «Создать партнёрскую ссылку» сначала ведёт в аналитику — P3

У партнёра без основной ссылки публикация предлагает «Создать партнёрскую ссылку →». Переход ведёт на `/links?view=links&programId=...`, где открывается «Аналитика → Постоянные ссылки». Для формы нужно ещё нажать «Создать ссылку». После создания автоматического возвращения к исходной карточке нет; Back проходит промежуточные страницы и теряет карточку, как в C03.

**Код:** [MaterialEditor.tsx](../../apps/portal/src/pages/MaterialEditor.tsx), строка 57.

**Исправление:** вести непосредственно к существующей форме создания основной ссылки и сохранить контекст возврата к материалу. Новая форма или новый тип ссылки не нужны.

## Как сейчас устроены файлы и ручная публикация

Проверенный путь:

1. «Материалы» → «Загрузить файлы»: по умолчанию несколько файлов прикрепляются к одному оригиналу.
2. «Отдельный материал для каждого файла»: два выбранных файла действительно создали две отдельные заготовки по одному файлу.
3. Заготовку можно оставить без даты и затем назначить день либо прикрепить к пустой задаче соответствующего формата.
4. В карточке «Материал» редактируются текст, дата, время, вложения и готовность.
5. В карточке «Публикация» сохраняются текст и список файлов. Небольшая кнопка со стрелкой скачивает каждый файл. Проверочный TXT скачался в Windows Downloads: **121 байт, SHA-256 совпал с оригиналом**.
6. «Копировать текст и ссылку» скопировало текст и отслеживаемую ссылку с параметрами размещения. Повторное копирование не должно создавать другое размещение; существующие API-тесты проверяют идемпотентность связанных операций.
7. «Открыть площадку» ведёт на соответствующий сайт; файлы партнёр прикрепляет там вручную. После публикации можно сохранить HTTPS-адрес и отметить размещение опубликованным. HTTP/local-адрес публикации был корректно отклонён.

**Сейчас нет** автоматической отправки файлов в соцсеть, общей ZIP-выгрузки или подтверждения соцсетью факта публикации. Отметка «Опубликовано» — самостоятельное подтверждение партнёра. Соцсеть и её авторизованная загрузка в этой проверке не использовались.

UX загрузки/скачивания требует яснее показать действие скачивания; интерфейс сейчас даёт только маленькую иконку. По коду скачивание использует общий обработчик сохранения: временно выставляет busy, сбрасывает «Сохранено» и инвалидирует данные календаря/аналитики. Это лишняя работа для read-only операции; устойчивое визуальное мигание в этой проверке отдельно не измерялось.

Вложения защищены авторизацией. Существующий интеграционный тест проверил 401 без входа, `private, no-store`, Content-Disposition attachment, повтор загрузки с тем же ID, отказ подменённых файлов и защиту файлов опубликованного материала. Эти проверки не являются полноценным аудитом безопасности загрузок.

## Сверка атрибуции и денег

В изолированный API внесены синтетические события с известными итогами. Это реальные записи тестовой среды, а не нарисованные промежуточные значения графиков.

| Область | Переходы | Регистрации | Платящие клиенты | Оплаты | Деньги клиентов | Комиссия |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| Основная ссылка / весь партнёр | 7 | 4 | 3 | 4 | 2 500 ₽ | 500 ₽ |
| Оба материала сценария | 5 | 3 | 2 | 3 | 2 200 ₽ | 440 ₽ |
| Заготовка → задача → Telegram | 3 | 2 | 1 | 2 | 1 500 ₽ | 300 ₽ |
| Ручной материал → ВКонтакте | 2 | 1 | 1 | 1 | 700 ₽ | 140 ₽ |
| Без привязки к публикации | 2 | 1 | 1 | 1 | 300 ₽ | 60 ₽ |

Основная ссылка показывает **7 всего, включая 5 у публикаций**, не 12. Первых оплат 3, повторных 1. Суммы временных рядов совпали с итогами отчёта. Тот же общий итог вернули администратор и факты калькулятора. Отбор одного сценария корректно исключил непривязанные переходы.

Проверено отдельно: регистрации/оплаты сегодня учитываются, даже если переход был за один-два дня до них. В «Сегодня» 3 перехода, но 4 регистрации — это допустимо по разным датам событий, не арифметическая ошибка.
