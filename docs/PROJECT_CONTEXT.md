## Запуск и два кабинета

Основная инструкция: [scripts/local-launcher/README.md](../scripts/local-launcher/README.md).

Для совместной работы нужен Codex с этой папкой проекта и действие **«Запустить Syntolk»**. Оно настроено в [.codex/environments/environment.toml](../.codex/environments/environment.toml) и запускает из корня:

```powershell
powershell.exe -NoProfile -File "scripts/local-launcher/start-codex.ps1"
```

Скрипт поднимает/переиспользует сервисы и готовит локальный вход. После запуска открой или обнови две встроенные вкладки Codex. Само выполнение скрипта не является проверкой открытых и авторизованных кабинетов.

Для нового профиля браузера сначала запусти действие. Если вход не сохранился, на `/login` используй поле **«Файл локального входа»**:

- администратор: `.local-demo/browser-login/admin.ticket.json`;
- партнёр: `.local-demo/browser-login/partner.ticket.json`.

Это одноразовые билеты на 10 минут, привязанные к origin и роли. Они не содержат API-ключа, но дают возможность входа: не печатай и не публикуй их содержимое. Повторный запуск действия обновляет билеты. Действующий локальный вход сохраняется; выход из кабинета удаляет его. Dev-механизм не должен попадать в production.

Существующий источник администраторского входа — только значение `ADMIN_API_KEY` из корневого `.env`; партнёрский вход сохранён зашифрованным в `.local-demo/partner-login.encrypted.json`. Пользуйся готовым запускателем, не выводи значения и не создавай новые ключи при ошибках сети, базы или расшифровки.

Есть и отдельный Windows-запускатель: ярлык **Syntolk**, корневой `Запустить Syntolk.lnk` и `.local-demo/launcher/Syntolk.exe`. Это отдельное окно с собственным браузерным профилем. Для работы с комментариями к страницам используй вкладки Codex; вход в EXE не равен входу в них.

## Важные продуктовые договорённости

- Это связанная система: сценарий калькулятора → календарь/задачи → материал → размещения/отслеживаемые ссылки → переходы, регистрации, оплаты и комиссии. Изменение одного экрана не должно терять связи с остальными.
- Партнёр может создать отслеживаемую ссылку на публикацию без калькулятора. Сценарий — дополнительная связь, а не обязательное условие для любой публикации.
- В «Публикациях и ссылках» нужны оба раздела: создание и аналитика. Новая форма не заменяет и не удаляет существующий отчёт.
- Постоянная партнёрская ссылка и ссылка конкретной публикации — разные уровни детализации одной системы атрибуции. Если общий отчёт показывает 100 переходов, из которых 40 у публикации, итог остаётся 100. Не суммируй повторно родительские и дочерние результаты.
- Создание ссылки, подготовка материала и отметка публикации — не одно событие. Не называй материал опубликованным только потому, что ему выдана ссылка; не подменяй дату публикации датой создания.
- Один оригинальный материал может иметь несколько размещений на разных площадках/каналах. Не увеличивай число уникальных материалов за счёт копий. Не дублируй размещение при повторном копировании ссылки.
- Не приписывай неизвестным старым событиям сценарий, площадку или материал по догадке. Отсутствие привязки нужно отличать от нулевых результатов.
- «Мой сценарий» — прогноз по плану; «Текущие значения» — факт за выбранную область и период. Не выдавай фактическую комиссию за прогноз первого месяца и не умножай её на число месяцев.
- Фактические количества материалов, переходов, регистраций и оплат должны происходить из реальных событий. Просмотры партнёр может дополнять вручную. Для конверсии нужны согласованные числитель, знаменатель и область расчёта; отсутствующие просмотры не превращай в выдуманный CTR.
- Платящий клиент и количество его оплат — разные метрики. Деньги клиентов, начисления партнёру и выплаченные средства — разные финансовые показатели. Уникальных клиентов нельзя безусловно суммировать по строкам.
- Два периода сравнения выбираются независимо и могут иметь разную длину. Для всех карточек, графиков и таблиц применяются те же диапазоны. Проверяй включение последнего дня, часовой пояс и пустые периоды; не скрывай позднюю оплату лишь потому, что переход был раньше.
- Новые пользовательские площадки и форматы должны быть доступны общей аналитике и фильтрам, в том числе администратора. Не подменяй их обрезанным статическим списком.
- Фильтр активности списка не должен неожиданно менять общие суммы отчёта. Область сценария, контента, партнёра и дат должна оставаться понятной и одинаковой в сравниваемых представлениях.
- Поддерживай согласованность общей аналитики администратора и партнёра при одинаковой области расчёта, правах и фильтрах. Возвраты, тестовые/подозрительные события и финансовые округления должны учитываться одинаково.

Эти договорённости задают критерии проверки, но не утверждают, что каждый пункт уже реализован без ошибок. Не начинай исправлять их все без нового задания.

## Дизайн: что не повторять

Пользователь неоднократно отклонял самовольные переделки калькулятора, удаление аналитики и фильтров, огромные поясняющие блоки, дублирование подписей и яркие эффекты при наведении. Сохраняй согласованный текущий интерфейс и меняй конкретно запрошенное.

Спокойное наведение без zoom/scale и без скачков макета. Стандартные активные переключатели и тему сохраняй: промежуточная просьба перекрасить всё в серый была затем отозвана. Не трактуй её как действующий приказ убрать все смысловые и фирменные цвета. Калькулятор в разных режимах должен оставаться тем же интерфейсом, а главная — давать доступ к работе на день и трём существующим быстрым действиям.

## Проверки

Выбирай проверки по текущему изменению. Примеры команд из корня проекта:

```powershell
# Точечные тесты портала: укажи нужный файл вместо запуска всех модулей.
pnpm --filter @openpartner/portal exec vitest run src/pages/CalculatorCurrentValues.test.tsx
pnpm --filter @openpartner/portal exec vitest run src/pages/PublicationsPage.test.tsx src/pages/Links.test.tsx

# Проверки механизма запуска и входа без вывода сохранённых ключей.
node --test scripts/local-launcher/credentials.test.mjs scripts/local-launcher/browser-login.test.mjs

# Сборка только нужного компонента, если она требуется задачей.
pnpm --filter @openpartner/portal build
pnpm --filter @openpartner/api build
pnpm --filter @openpartner/router build
```

Для серверной аналитики смотри связанные тесты в `apps/api/src/coach/__tests__/`, включая `admin-analytics-parity.test.ts`, `analytics-golden.test.ts` и `calculator-current-values.test.ts`. До запуска проверь изоляцию тестов от рабочей БД. Не создавай реальные регистрации, переходы и оплаты в пользовательской статистике ради smoke-теста без разрешения.

UI проверяй в браузере: обе роли при общих изменениях, режимы калькулятора, даты/пустые диапазоны, раскрытие деталей и клики по графикам, отсутствие потери аналитики и скачков макета. Проверка HTTP 200 или успешная сборка не заменяет визуальную проверку.
